# Architecture notes

Decisions and assumptions made during Phase 0 and Phase 1. `CLAUDE.md` remains the specification;
this file records how it has been interpreted so far and why.

## Repository

- **npm workspaces.** npm ships with Node.js and was the only package manager installed, so no
  extra tooling is needed. Nothing depends on npm-specific behaviour.
- **Source-only packages.** `@medos/shared` and `@medos/ui` export TypeScript source. The web app
  compiles them (`transpilePackages`), and Vitest reads them directly. There is no package build
  step to keep in sync.
- **Packages are created when needed.** `@medos/database` arrived with Phase 2 (see
  [`database.md`](database.md)), `apps/sync` with Phase 5, `@medos/parsers` with Phase 6 and `@medos/storage` (the object store, shared by the sync and
  the web app) with Phase 7
  (see [`parsing.md`](parsing.md)); `@medos/fsrs` (flashcard scheduling) with Phase 11; `study-engine` is not scaffolded yet. `@medos/shared` is deliberately free of browser and
  framework dependencies so the future sync CLI and database package can use it.
- **One lint, format and unit-test configuration at the root.** Type-checking runs per workspace.

## Web application

- **Route group `(app)`** wraps the study workspace in the application shell. The future `/login`
  route sits outside it and renders without the shell.
- **Server components by default.** Client components are limited to things that need the
  browser: navigation state, theme controls, dialogs, tabs and the search field.
- **No global state library.** The only client state is two per-device preferences (theme and
  sidebar), held in a small `localStorage` store read through `useSyncExternalStore`.
- **Theme and sidebar state are applied by an inline script in `<head>`** before first paint, as
  `data-theme` and `data-sidebar` on `<html>`. Styling then follows from CSS alone, which avoids a
  flash of the wrong theme and any hydration mismatch.
- **Container queries for page layout.** The workspace is a CSS container, so pages respond to the
  space they actually have rather than to the viewport.
- **Fonts are self-hosted** from npm packages (Inter for the interface, Source Serif 4 for
  headings). Builds need no network access and no third party sees page loads.

## Authentication boundary

Added in Phase 3 and described in [`authentication.md`](authentication.md). The points that shape
other code:

- **Everything is private by default.** Public paths are an allow-list in
  `src/server/auth/routes.ts`; a new route is private without any extra work.
- **Each private page verifies the session itself** with `requireUser()`. A layout cannot do this
  for its children, because layouts are not re-run on navigation. A test enforces it.
- **Study data is reached only through `getUserScope()`**, which binds every query to the signed-in
  user. Code outside `src/server` cannot import the database handle (ESLint rule).
- **Workspace pages are rendered per request.** Nothing private is prerendered at build time.
- **The database connection is opened lazily** on first use and kept on `globalThis`, so builds
  never touch the database and development reloads do not open a second connection.

## Data seams

- `getTodayOverview()` in `apps/web/src/features/today` is the single source for the Today screen.
  It returns a typed development fixture tagged `source: "fixture"`, and the page shows a notice
  whenever that tag is present. Replacing the function body with database queries requires no
  change to the page.
- Courses, the semester calendar and default study availability are constants in `@medos/shared`.
  They will seed the database in Phase 2.
- Calendar dates are handled as `YYYY-MM-DD` strings and computed in UTC, so week numbers and
  countdowns do not depend on the server or browser time zone.

## Assumptions to revisit

- **Teaching weeks** are counted in 7-day blocks from the first day of term (28 September 2026 is
  week 1). Holiday weeks are not skipped, because the winter break dates are not in the
  specification yet.
- **Assignments** are grouped with university events in the calendar legend; study sessions,
  revision and personal events are the user's own.
- **Winter holiday** is not shown in the academic calendar because its dates have not been
  provided.
- **`apps/web/AGENTS.md` and `apps/web/CLAUDE.md`** are generated by `next dev` (Next.js 16.3+) to
  point coding agents at the version-matched documentation bundled with Next.js. They are
  committed because Next.js recreates them; set `agentRules: false` in `next.config.ts` to opt out.

## Study Guide reader

Added in Phase 7 and described in [`reader.md`](reader.md). The points that shape other code:

- **Content is server-rendered; interaction is in small client islands.** The guide's blocks are
  server components. Contents, the selection toolbar, section actions, the context panel and the
  progress tracker are client components that never change the rendered text. After an
  annotation changes, the Server Function calls `refresh()` and the server renders the marks.
- **One addressing scheme.** Text units and anchors are defined in `@medos/parsers/model`
  (`text-units.ts`) and used by the renderer, the browser's selection code and the server's
  validation alike.
- **User data never lives in parsed content.** Annotations and reading progress are their own
  tables, anchored to the content, so re-processing a file cannot erase them.
- **Wide pages opt in.** A page marked `data-layout="wide"` may use more of the workspace than
  the usual 1080px; only the reader does.
